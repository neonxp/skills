# spec-2-plan — технический план

Спека говорит **что** строим; план — **как**. План фиксирует технические решения
с обоснованием, до того как написан код: менять абзац плана дёшево, менять
архитектуру после — дорого. План не добавляет требований: новое требование —
повод вернуться в `spec-1-specify`.

> **Приоритет правил:** если в корне проекта есть `rules.md`, его инструкции
> превалируют над любыми правилами этого скилла — даже противоречащими им.
>
> **Вопросы пользователю:** если на вопрос возможны варианты ответа — задавай его
> штатным инструментом вопросов с вариантами (в pi — ask_user_question, в других
> агентах — их аналог). Открытый текст — только когда варианты подобрать нельзя.

## Место в процессе

```
specify → [plan] → tasks → implement → verify → archive
 спека    техплан  задачи     код      сверка   закрытие
```

Малому изменению (пара файлов, тривиальный путь) план в отдельном файле не нужен —
подход в двух строках можно держать прямо в разговоре. План обязателен, когда
выбор решения неочевиден, затрагиваются данные/контракты/несколько модулей.

## Workflow

- [ ]   1. Открой `specs/<id>-<slug>/spec.md`. Если остались `[УТОЧНИТЬ]` или статус
       «черновик» без согласования — сначала закрой вопросы с пользователем;
       планировать по несогласованной спеке нельзя.

- [ ]   2. Изучи кодовую базу в зоне изменения:
        - Если в корне есть `MINDMAP.md` — начни с него: домены, модели и потоки
          покажут, где какая ответственность живёт (карта от скилла `mindcode`;
          её наличие не обязательно).
        - Если есть `AGENTS.md` — учти принципы и ограничения проекта.
        - Если есть `rules.md` — учти git-процесс и ревью-конвенции (ревью плана:
          да/нет, кто ревьюит).
        - Иначе читай затрагиваемые модули выборочно: точки входа, контракты, 1–2
          файла-представителя на модуль.

- [ ]   3. Если решение неочевидно — сравни 2–3 варианта до выбора: стоимость,
       риски, совместимость. Отвергнутые альтернативы записывай: они спасут
       от повторного обсуждения.

- [ ]   4. Заполни `specs/<id>-<slug>/plan.md` по шаблону [templates/plan.md](templates/plan.md):
       подход, решения (D#), затрагиваемый код, данные и контракты, ограничения.
       Долгие исследования выноси в `research-<тема>.md` рядом, в плане — вывод.

- [ ]   5. Проверь себя:
        - каждое требование спеки покрыто подходом (пробегись по R#);
        - план не добавляет новых требований и не меняет старые;
        - «Затрагиваемый код» конкретен — по нему будут резаться задачи;
        - нет листингов кода — только решения и границы.

- [ ]   6. Покажи план пользователю на короткое ревью: решения (D#) и затрагиваемый
       код — самое важное. Предложи варианты: «Принимаю», «Нужны правки». Правь по замечаниям.
       В команде — коммит плана в ветку `<id>-<slug>` до кода.

- [ ]   7. Отчитайся: путь к плану, ключевые решения одной строкой каждое,
       следующий шаг — `spec-3-tasks`. Явно сообщи это пользователю:
       «Следующий этап — создание задач по плану. /spec-3-tasks»

## Gotchas

- **Планирование по черновику спеки** — потерянное время: сначала согласуй спеку.
- **План-переписка спеки** — если в плане появляются новые «система ДОЛЖНА», это
  требования; перенеси их в spec.md.
- **Скрытые технологии** — выбор библиотеки/СУБД это решение D#, а не «и так
  очевидно»: запиши и обосновай.
- **Контракт для другой команды** — выноси в отдельный файл и ревьюй отдельно:
  это самая дорогая для изменения вещь.
- **Разросшийся план** — больше ~2 экранов: детали в research-файлы, план — решения.
