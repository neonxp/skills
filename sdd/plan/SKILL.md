# plan — модуль DAG-планирования

План — JSON-файл в проекте пользователя; порядок исполнения не хранится,
а вычисляется скриптом из зависимостей. Скрипт делает всё детерминированное
(графы, порядок, готовность), агент — всё осмысленное (декомпозиция, ТЗ,
проверки). Правишь план — прогоняй `validate`.

> **Приоритет правил:** если в корне проекта есть `rules.md`, его инструкции
> превалируют над любыми правилами этого скилла — даже противоречащими им.
>
> **Вопросы пользователю:** если на вопрос возможны варианты ответа — задавай его
> штатным инструментом вопросов с вариантами (в pi — ask_user_question, в других
> агентах — их аналог). Открытый текст — только когда варианты подобрать нельзя.

## Где живёт план

- `.specs/<id>-<slug>/plan.json` — план изменения из sdd-цикла (рядом с tasks.md;
  архивируется вместе со спекой).
- `plans/<slug>/plan.json` — автономный план (итеративная разработка, разросшаяся
  задача task-loop).

## Формат plan.json

Схема: [schemas/plan.schema.json](schemas/plan.schema.json) (справочник и
подсказки редакторам; рантайм-проверку делает `validate`). Каркас:
[templates/plan.json](templates/plan.json).

```json
{
    "version": 1,
    "title": "Авторизация",
    "description": "JWT-аутентификация",
    "source": ".specs/001-auth",
    "steps": {
        "gate-tests": {
            "type": "milestone",
            "title": "Ворота: интеграция",
            "parent": null,
            "deps": ["auth-model"],
            "status": "pending",
            "prompt": "Коротко: что ворота проверяют",
            "criteria": ["command: go test ./internal/auth/..."],
            "result": null
        },
        "auth-model": {
            "type": "task",
            "title": "Модель пользователя",
            "parent": "gate-tests",
            "deps": [],
            "status": "pending",
            "prompt": "Полное ТЗ для исполнителя без контекста",
            "criteria": ["command: go build ./..."],
            "result": null,
            "task": "T1",
            "requires": ["R1"],
            "phase": "Фундамент"
        }
    }
}
```

Ключевые поля:

- **type** — `task` (атомарная работа), `research` (произвести знание/артефакт),
  `milestone` (интеграционные ворота блока; проверка дорогая, локальная, без
  субагента).
- **prompt** — главное поле: исчерпывающее самодостаточное ТЗ для исполнителя,
  который не видит этого разговора: файлы, поведение, крайние случаи, ограничения.
  У milestone — короткая сводка того, что ворота проверяют.
- **criteria** — проверки; `command: ...` — исполняемая команда, остальное —
  проверяемое агентом наблюдение.
- **parent** — неявная зависимость «родитель ждёт всех детей» (её в deps
  дублировать не нужно).
- **status** — `pending | active | done | skipped | failed`; закрытыми считаются
  `done` и `skipped`.
- **task / requires / phase** — необязательная связь с tasks.md (метка задачи,
  трассировка [R#], фаза) для `sync`.

## Команды

Везде: `python3 <каталог скилла plan>/scripts/plan.py <команда> <plan.json> …`

| Команда                 | Назначение                                                                                                                                |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `validate`              | Структура, битые ссылки, циклы (с выводом цепочки)                                                                                        |
| `next`                  | Готовые шаги (зависимости закрыты) в топологическом порядке: JSON со state (`running`/`wait`/`done`), remaining и полными prompt/criteria |
| `groups`                | Уровни параллельного исполнения                                                                                                           |
| `status`                | Сводка: счётчики по статусам, процент                                                                                                     |
| `set <id> <статус>`     | Сменить статус шага (`--result "итог"`)                                                                                                   |
| `render`                | Mermaid-граф + чеклист — для показа пользователю                                                                                          |
| `sync --tasks tasks.md` | Проставить чекбоксы в tasks.md по меткам task                                                                                             |

## Workflow модуля

- [ ]   1. Декомпозиция **сверху вниз**: сначала крупные блоки (milestone-ворота),
       затем их подшаги (parent), затем под-подшаги; стремись к 3 уровням.
       Порядок между сиблингами — через deps. Не можешь назвать подшаги блока —
       либо не понял его, либо он атомарен; во втором случае не дроби.
- [ ]   2. Напиши plan.json по каркасу и прогони `validate`.
- [ ]   3. **Ворота старта:** покажи пользователю граф (`render`) и спроси
       (вариантами): «Стартую план?» / «Сначала правки». Правки — правь файл,
       снова `validate`; не пересобирай план с нуля.
- [ ]   4. Цикл исполнения: `next` → возьми шаг и сразу `set <id> active` →
       работа по prompt (субагенту, если он есть, — prompt и есть бриф;
       milestone проверяй сам) → прогони criteria локально → всё зелёное:
       `set <id> done`, иначе `set <id> failed --result "что не так"`,
       исправь и повтори.
- [ ]   5. После каждого `set` — чекбоксы и витрина: над планом с task-метками
       — `sync` (чекбоксы tasks.md обновляет скрипт, не вручную); если план
       живёт в `.specs/` (sdd-изменение) и дашборд витрины уже собран —
       пересобери его: `python3 <каталог скилла spec-1-specify>/scripts/
       build-dashboard.py`. Открытая вкладка дашборда обновится сама —
       повторно её не открывай.
- [ ]   6. Новая работа по ходу — новый шаг в plan.json (+ задача в tasks.md),
       `validate`, дальше по циклу. `state: done` — план закрыт.

## Gotchas

- **Правка порядка руками** — порядок не хранится, он вычисляется; не «ставь
  шаг выше», а прописывайте deps.
- **Цикл зависимостей** — validate назовёт цепочку; разорви в слабом звене.
- **Мilestone как задачи** — ворота не делегируй субагенту: их критерии —
  интеграционные, проверяются локально оркестратором.
- **План без prompt'ов** — шаг «сделай X» без файлов и поведения бесполезен:
  исполнитель не видел чат.
