# spec-3-tasks — декомпозиция на задачи

Задачи — мост между планом и кодом: каждая трассируется к требованию, каждая
проверяема, каждая понятна исполнителю, который не видел этого разговора. Плохая
задача («сделать фичу») прячёт решения; хорошая называет файлы, поведение и способ
проверить.

> **Приоритет правил:** если в корне проекта есть `rules.md`, его инструкции
> превалируют над любыми правилами этого скилла — даже противоречащими им.
>
> **Вопросы пользователю:** если на вопрос возможны варианты ответа — задавай его
> штатным инструментом вопросов с вариантами (в pi — ask_user_question, в других
> агентах — их аналог). Открытый текст — только когда варианты подобрать нельзя.

## Место в процессе

```
specify → plan → [tasks] → implement → verify → archive
 спека   техплан  задачи      код      сверка   закрытие
```

## Workflow

- [ ]   1. Открой `.specs/<id>-<slug>/`: plan.md обязателен, спека — источник [R#].
       План-файла нет, а изменение крупное — вернись к `spec-2-plan`.

- [ ]   2. Заполни `tasks.md` по шаблону [templates/tasks.md](templates/tasks.md):
        - **Фаза 1 «Фундамент»** — общая подготовка (схемы, каркас, конфигурация)
          без неё требования не начинать. Не раздувать.
        - **Фаза 2 «Требования»** — задачи по R# в порядке важности; внутри
          требования тесты (если проект их пишет) до кода.
        - **Фаза 3 «Полировка»** — документация, чистка, прогон критериев приёмки.

- [ ]   3. Правила каждой задачи:
        - **[R#]** — какое требование закрывает; без метки только фундамент/полировка.
        - **[P]** — можно параллельно (разные файлы, нет зависимостей); задачи
          с общим контрактом — не [P]: сначала задача, фиксирующая контракт.
        - **≤ 5 файлов** и одна фокус-сессия; крупнее — дели. «И» в названии —
          признак двух задач; критериев проверки больше трёх — дели.
        - **Рабочее состояние** — после каждой задачи система собирается и живёт;
          «сломано, починим потом» — дыра в плане, а не следующий шаг.
        - **Точка отката** — задача независимо откатываема: аддитивное лучше
          модификаций; миграции — с откатной миграцией; «удалить и заменить
          здесь же» — не в одной задаче.
        - **Проверка** — исполняемая команда (`go test ./internal/auth/...`) или
          наблюдаемое поведение; «работает» — не проверка.
        - **Самодостаточный текст** — исполнитель-субагент или коллега не видят
          чат: файлы, поведение, крайние случаи — прямо в задаче.

- [ ]   4. Отметь **контрольные точки**: где останавливаемся и показываем
       пользователю результат (обычно — после фазы 2: проживаемый сценарий).

- [ ]   5. Проверь трассировку и полноту:
        - каждый R# из spec.md закрыт хотя бы одной задачей;
        - каждая задача ссылается на R# (или честно лежит в фундаменте/полировке);
        - файлы задач не выходят за «Затрагиваемый код» из plan.md;
        - задач с «а заодно…» нет — это отдельные изменения.

- [ ]   6. Покажи пользователю **полный текст tasks.md** на ревью — не «задачи
       готовы, гляньте», а весь список — и предложи варианты: «Принимаю» /
       «Нужны правки». Правь по замечаниям и повторяй ревью. В команде — задачи
       едут в ветке вместе со спекой и планом, ревью до кода. Конвенции ревью —
       в `rules.md`, если он есть.

- [ ]   7. Задач **≥ 3 или есть [P]-задачи**? Собери машинный план `plan.json` рядом
       с tasks.md по модулю plan (набор plan): каждой задаче — шаг с той же меткой
       `task`, исчерпывающим prompt-ТЗ и проверкой из «— проверка:»; зависимости —
       из порядка и [P]-меток; интеграционные проверки — milestone-шаги. Прогони
       `validate`. Задач мало и всё линейно — пропусти, исполнение пойдёт по
       tasks.md.

- [ ]   8. Пересобери дашборд витрины: `python3 <каталог скилла spec-1-specify>/scripts/build-dashboard.py`.

       Если в системе есть `xdg-open` (Linux) или `open` (macOS) и дашборд ещё
       не открыт — открой его: открытая вкладка обновляется сама при
       пересборках, новые вкладки не открывай.

- [ ]   9. Отчитайся: путь к tasks.md (и plan.json, если собран), число задач по
       фазам и явно сообщи следующий шаг: «Следующий этап — имплементация.
       /spec-4-implement».

## Gotchas

- **«Задачи и так очевидны»** — рационализация: запись вскрывает скрытые
  зависимости и забытые крайние случаи; план в голове не переживает смену
  сессии и компакцию контекста.
- **Задача вне требований** — «откуда она взялась?» либо удали, либо добавь
  требование в спеку через `spec-1-specify`.
- **Гигантская задача** — «реализовать модуль X» прячет все решения; режь по
  файлам и поведениям.
- **Файлы вне плана** — задача трогает код, которого нет в «Затрагиваемом коде»:
  обнови план или пересмотри задачу.
- **Перекрывающиеся файлы у [P]-задач** — параллельное исполнение конфликтует:
  убери [P] или разведи файлы.
- **Тесты ради галочки** — пиши тесты в задачах только если проект реально их
  ведёт; иначе проверка — команды/наблюдение.
