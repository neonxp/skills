# spec-4-implement — исполнение по задачам

Код пишется строго по задачам: взял → сделал → проверил критерием → отметил.
Свобода импровизации — только внутри задачи; объём и поведение задаёт спека.

> **Приоритет правил:** если в корне проекта есть `rules.md`, его инструкции
> превалируют над любыми правилами этого скилла — даже противоречащими им.
>
> **Вопросы пользователю:** если на вопрос возможны варианты ответа — задавай его
> штатным инструментом вопросов с вариантами (в pi — ask_user_question, в других
> агентах — их аналог). Открытый текст — только когда варианты подобрать нельзя.

## Место в процессе

```
specify → plan → tasks → [implement] → verify → archive
 спека   техплан задачи      код       сверка   закрытие
```

## Workflow

- [ ]   1. Открой `specs/<id>-<slug>/tasks.md` и найди первую невыполненную задачу
       в порядке фаз и зависимостей (не по «интересности»).

- [ ]   2. Сверься с контекстом: если в корне есть `MINDMAP.md` — он подскажет, где
       какая ответственность живёт (карта не обязательна, но экономит поиск).

- [ ]   3. Выполни задачу:
        - трогай только файлы задачи; вышло за границу — остановись и разберись;
        - тесты в задаче (если есть) — до кода;
        - после выполнения **прогони проверку задачи**; не прошла — исправь,
          прежде чем двигаться дальше.

- [ ]   4. Отметь чекбокс задачи `[x]` — только после пройденной проверки.

- [ ]   5. Закоммить логическую группу (в команде — в ветке `<id>-<slug>`; спека,
       план и задачи едут в тех же коммитах вместе с кодом). Конвенции веток/PR
       и переходы статусов трекера — в `rules.md`, если он есть (например, после
       имплементации может требоваться не «Done», а «Code Review»/«Testing»).

- [ ]   6. Обнаружил расхождение с реальностью? Спека обновляется **первой**:
        - код по-другому правильнее — правь spec.md/plan.md, потом код;
        - код остаётся по спеке — исправь код.
          Молча разъехаться нельзя: verify ловит, но дешевле не терять. Заметное
          отступление от плана фиксируй одной строкой в `research.md` директории
          изменения (создай файл, если его ещё нет).

- [ ]   7. Новая работа по ходу (упущенный случай, переработка) — это новая задача
       с [R#] и проверкой: допиши в tasks.md в нужную фазу. Вылезло требование —
       обнови спеку, потом добавь задачу.

- [ ]   8. Дошёл до **контрольной точки** (или задач на сессию хватила) — остановись
       и отчитайся: что готово, что проверено, что дальше. При наличии субагентов
       самодостаточную задачу можно делегировать: текст задачи — полный бриф,
       результат проверяешь критерием сам.

- [ ]   9. Все задачи `[x]`? Явно сообщи: «Следующий этап — сверка кода со спекой.
       /spec-5-verify».

## Gotchas

- **Проверка «на глаз»** — критерий задачи исполняемый; не прогнал — задача не готова.
- **Отметил до проверки** — смысл чекбокса умирает; verify не поверит tasks.md.
- **Творческий разлёт** — «заодно отрефакторил соседний модуль» = чужой объём
  в чужом PR; откатывай или оформляй отдельным изменением.
- **Спека отстала от кода** — не закрывай глаза: правь спеку в том же коммите.
- **Застрял в задаче** — не расширяй её молча; вернись к пользователю с вопросом.
