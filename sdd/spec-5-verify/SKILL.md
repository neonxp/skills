# spec-5-verify — сверка кода со спекой

Вопрос верификации — не «написан ли код», а «сделано ли то, о чём договорились».
Сверка идёт по спеке, а не по чекбоксам: tasks.md — презумпция, не доказательство.

> **Приоритет правил:** если в корне проекта есть `rules.md`, его инструкции
> превалируют над любыми правилами этого скилла — даже противоречащими им.
>
> **Вопросы пользователю:** если на вопрос возможны варианты ответа — задавай его
> штатным инструментом вопросов с вариантами (в pi — ask_user_question, в других
> агентах — их аналог). Открытый текст — только когда варианты подобрать нельзя.

## Место в процессе

```
specify → plan → tasks → implement → [verify] → archive
 спека  техплан  задачи     код       сверка    закрытие
```

## Классификация

Для каждого требования R# из spec.md:

| Класс          | Что значит                                     |
| -------------- | ---------------------------------------------- |
| `выполнено`    | Реализовано полностью, крайние случаи закрыты  |
| `частично`     | Есть, но не до конца (случай/ветка не покрыта) |
| `противоречит` | Код ведёт себя иначе, чем требует спека        |
| `сверх спеки`  | Код делает то, чего спека не просит            |

`сверх спеки` — не мелочь: это объём, который никто не согласовывал (или забыли
вписать в спеку, или убрать из кода).

## Workflow

- [ ]   1. Открой `specs/<id>-<slug>/`: spec.md (истина), tasks.md (претензии),
       plan.md (заявленный подход). Если в корне есть `rules.md` — там определено,
       что значит «готово» (обязательные команды) и куда ведёт вердикт (к закрытию,
       к тестированию, к ревью).

- [ ]   2. Пройди требования: для каждого R# найди реализацию в коде и присвой
       класс из таблицы. Пробуй сценарии «Дано/Когда/Тогда» буквально — по коду
       или запуском, если дёшево.

- [ ]   3. Прогони критерии приёмки A# из spec.md, каждый: подтвердился или нет.

- [ ]   4. Сверь задачи с реальностью: невыполненные чекбоксы при сделанном коде
       и наоборот — фиксируй.

- [ ]   5. Прогони тесты и сборку проекта (если есть), зафиксируй результат.

- [ ]   6. Составь отчёт:

        ```
        ВЕРИФИКАЦИЯ <id>-<slug>
        Требования:  R1 выполнено · R2 частично · R3 противоречит · R4 выполнено
        Сверх спеки: <файл/поведение без требования в спеке>
        Критерии:    A1 ✓ · A2 ✗ · A3 ✓
        Сборка/тесты: ✓ / <падения>
        Вердикт: нужны правки (R2, R3, A2) / готов к закрытию
        ```

- [ ]   7. Правки — по месту расхождения:
        - `противоречит`/`частично` — обычно чинится код; чинит `spec-4-implement`;
        - спека оказалась не права (требование нереализуемо/устарело) — обнови
          спеку через `spec-1-specify`, потом код;
        - `сверх спеки` — либо убрать из кода, либо признать требованием в спеке;
          решает пользователь.

- [ ]   8. После устранения — повтори сверку изменённого. Явно сообщи вердикт:
       «Готов к закрытию — следующий этап /spec-6-archive» либо «Нужны правки:
       <список> — вернитесь к /spec-4-implement». Решение пользователя запроси
       инструментом вопроса с вариантами, затем пересобери дашборд витрины:
       `python3 <каталог скилла spec-1-specify>/scripts/build-dashboard.py`.
       Если в системе есть `xdg-open` (Linux) или `open` (macOS) — сразу открой
       свежий дашборд в браузере.

## Gotchas

- **Сверка «по чекбоксам»** — tasks.md может лгать; истина — спека плюс код.
- **Сценарий «на бумаге»** — если сценарий дёшево воспроизвести запуском —
  воспроизводи, не верь коду на слово.
- **Тихий `сверх спеки`** — не пропускай «полезный» лишний код: не согласованный
  объём взрывается в ревью.
- **Верификация до конца имплементации** — бессмысленна; все задачи должны быть `[x]`.
- **Правки мимо спеки** — починил код против спеки «потому что так лучше» без
  обновления спеки — воспроизвёл расхождение.
