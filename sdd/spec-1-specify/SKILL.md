# spec-1-specify — спецификация изменения

Спецификация пишется до кода и становится источником истины: что строим, зачем и как
поймём, что готово. Код без спеки — гадание. Спека описывает **поведение**, а не
реализацию: «как» будет в плане (`spec-2-plan`).

> **Приоритет правил:** если в корне проекта есть `rules.md`, его инструкции
> превалируют над любыми правилами этого скилла — даже противоречащими им.
>
> **Вопросы пользователю:** если на вопрос возможны варианты ответа — задавай его
> штатным инструментом вопросов с вариантами (в pi — ask_user_question, в других
> агентах — их аналог). Открытый текст — только когда варианты подобрать нельзя.

## Место в процессе

```
[specify] → plan → tasks → implement → verify → archive
 спека    техплан  задачи     код      сверка   закрытие
```

SDD нужен, если изменение затрагивает больше 2 файлов, меняет контракт/данные/архитектуру или требования
неоднозначны. Однострочный фикс спеки не заслуживает.

## Workflow

- [ ]   1. Определи, новое ли это изменение или обновление существующего:
        - **Обновление** (та же цель, уточнение исполнения, сужение объёма) — правь
          существующие файлы в `specs/<id>-<slug>/`, не создавай новое.
        - **Новое** (сменился intent, объём разросся до другой работы) — создавай новое.
          Не уверен — спроси инструментом вопроса с вариантами (Обновление / Новое).

- [ ]   2. Выбери идентификатор: `<id>-<slug>`.
        - `<id>` — внешний идентификатор задачи, если есть (`PRJ-123`), иначе порядковый
          `NNN` (найди максимум по `specs/` и инкрементируй).
        - `<slug>` — короткое kebab-case имя по-английски (`dark-mode`, `rate-limit-login`).
        - Примеры: `PRJ-123-dark-mode`, `004-rate-limit-login`.

- [ ]   3. Разберись в контексте:
        - Изучи если есть `specs/_system/` - общее описание проекта
        - Если в корне есть `rules.md` — прочитай: конвенции команды (трекер,
          ревью, артефакты) переопределяют дефолты скилла
        - Если в корне проекта есть `MINDMAP.md` — начни с него: домены, модели и потоки
          сэкономят чтение кода. (Скилл `mindcode` ставит эту карту; его наличие
          не обязательно — просто пользуйся картой, если она есть.)
        - Если есть `AGENTS.md` — учти зафиксированные в нём принципы и ограничения.
        - Иначе изучи затрагиваемый код напрямую — выборочно, не весь проект.
          И внеси находки в research.md в директории спеки.
        - Если есть внешний id задачи в таск трекере И есть mcp/api к таск трекеру — изучи задачу по
          нему (сначала спроси разрешения пользователя!). Доступ к трекеру описан
          в `rules.md`, если он есть.

- [ ]   4. Собери вводные от пользователя. Прежде чем писать спеку, выпиши **допущения**
       — всё, что ты придумал за пользователя:
        ```
        ДОПУЩЕНИЯ (поправь, если не так):
        1. Аутентификация — сессии в куках, не JWT
        2. Целевая СУБД — PostgreSQL (по существующей схеме)
        → Поправь сейчас, иначе иду с этим.
        ```
        Ничего не оставляй неявным: расплывчатое требование («сделай быстрее»)
        переформулируй в измеримый критерий («первая отрисовка < 2.5 c на 4G»).

- [ ]   5. Создай каталог `specs/<id>-<slug>/` и заполни файлы по шаблонам скилла:
        - [templates/proposal.md](templates/proposal.md) → `proposal.md` — зачем и что,
          границы (внутри/вне объёма), внешние ссылки.
        - [templates/spec.md](templates/spec.md) → `spec.md` — требования + сценарии +
          критерии приёмки. Если меняется уже описанное в `specs/_system/` поведение —
          используй секции «Изменяется»/«Удаляется» с полным новым текстом требования.
        - [templates/research.md](templates/research.md) → `research.md` — накопитель
          находок из шага 3 и последующих этапов.

- [ ]   6. Пересобери дашборд витрины (запуск из корня проекта) — он создаётся
       здесь и дальше пересобирается каждым скиллом цикла; коммить его вместе
       с артефактами. Правится только через файлы-источники, не вручную:

       ```bash
       python3 <каталог скилла spec-1-specify>/scripts/build-dashboard.py
       ```
       Если в системе есть `xdg-open` (Linux) или `open` (macOS) — сразу открой
       свежий дашборд в браузере.

- [ ]   7. Сформулируй **уточняющие вопросы** — то, без чего спека врёт или молчит.
       Проверь покрытие по рубрикам: объём и границы; роли и права; данные и их
       жизненный цикл; состояния ошибок и крайние случаи; нефункциональное
       (производительность, безопасность, наблюдаемость); интеграции и их сбои;
       терминология. Задавай штатным инструментом вопросов с вариантами ответов
       (в pi — ask_user_question) столько вопросов, сколько нужно для точной
       спеки — без искусственных лимитов: лучше больше точных вопросов, чем
       меньше расплывчатых. Каждый с подобранными вариантами и возможностью
       свободного ответа; открытый текст — только когда варианты невозможны.
       Вопросов много — разбивай на блоки по рубрикам. В тексте спеки
       ставь маркер `[УТОЧНИТЬ: вопрос]` вместо выбора за пользователя.

- [ ]   8. Покажи пользователю спеку на ревью — это обязательная точка:
        - Соло: презентуй краткое резюме (зачем, что, границы, открытые вопросы) и дай
          прочитать файлы. Не просто спроси «принимаем спеку?» а именно дай полный её
          текст, чтобы пользователь ознакомился! Правки вноси в файлы (сам или по
          замечаниям) и повторяй ревью — до явного согласия через инструмент
          вопроса с вариантами («Принимаю» / «Нужны правки»).
        - Команда: предложи закоммитить спеку в ветку `<id>-<slug>` и получить ревью
          спеки **до** кода (отдельным мини-PR или ревью в чате — как принято в проекте).
          Правки вноси в файлы (сам или по замечаниям) и повторяй ревью. «Дёргать назад
          дёшево»: правка абзаца спеки почти бесплатна, правка 300 строк кода — нет.

- [ ]   9. Отчитайся: путь к каталогу, число требований и сценариев, открытые
       `[УТОЧНИТЬ]`, следующий шаг — `spec-2-plan`. Явно сообщи это пользователю:
       «Следующий этап — планирование. /spec-2-plan»

## Что делает требование хорошим

- Одно требование — одно наблюдаемое поведение с «ДОЛЖНА»/«ДОЛЖЕН». Три «и ещё» —
  это три требования, раздели.
- Наблюдаемость: человек вне кода может проверить. «Система ДОЛЖНА показывать баннер
  ошибки при загрузке > 10 МБ» — да; «ДОЛЖНА обрабатывать большие загрузки» — нет.
- Сценарий проверяет требование конкретной ситуацией (Дано/Когда/Тогда), а не
  пересказывает его другими словами.
- Крайние и ошибочные случаи важнее happy path: пустой ввод, истёкший токен,
  повторный клик. Спроси себя: «какой случай меня разозлит, если сломается?» —
  и убедись, что для него есть сценарий.
- В требованиях нет реализации: очередь, библиотека, схема таблиц — это для плана.

## Gotchas

- **Не пиши код и не трогай исходники** — только `specs/<id>-<slug>/`.
- **Не выбирай технологию в спеке** — даже если очевидно; её место в `plan.md`.
- **Не молчи о неоднозначности** — `[УТОЧНИТЬ]` лучше красивой догадки.
- **Молчаливое расширение объёма** — если в proposal пролезло «а заодно поправим…»,
  вынеси это в отдельное изменение.
- **`specs/` ещё нет** — создай каталог; для нового домена не забудь поле
  «Домен» в spec.md — по нему при закрытии изменение вольётся в `specs/_system/`.
- **Правка после начала кода** — нормальна: спека живая, обнови её и скажи,
  что изменилось.
