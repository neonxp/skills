# spec-6-archive — закрытие изменения

Закрытие фиксирует истину: дельты изменения вливаются в накопительную спеку
системы, само изменение уезжает в архив с датой. Через полгода архив объясняет,
почему код выглядит именно так.

> **Приоритет правил:** если в корне проекта есть `rules.md`, его инструкции
> превалируют над любыми правилами этого скилла — даже противоречащими им.
>
> **Вопросы пользователю:** если на вопрос возможны варианты ответа — задавай его
> штатным инструментом вопросов с вариантами (в pi — ask_user_question, в других
> агентах — их аналог). Открытый текст — только когда варианты подобрать нельзя.

## Место в процессе

```
specify → plan → tasks → implement → verify → [archive]
 спека   техплан задачи     код      сверка    закрытие
```

## Workflow

- [ ]   1. Проверь готовность — без всех трёх закрытия нет:
        - вердикт `spec-5-verify` — «готов к закрытию»;
        - все критерии приёмки A# в spec.md отмечены `[x]`;
        - открытых `[УТОЧНИТЬ]` и незакрытых вопросов нет.

- [ ]   2. Влей дельты в накопительную спеку `specs/_system/<домен>.md`
       (домен — из поля «Домен» в spec.md):
        - **Добавляется** — требования дописываются в конец;
        - **Изменяется** — требование с тем же R# заменяется полным новым текстом;
        - **Удаляется** — требование убирается; если у домена не осталось требований —
          спроси пользователя и удали файл (или оставь с пометкой «упразднён»);
        - файла домена ещё нет — создай: заголовок `# <Домен>`, раздел
          `## Назначение` (2–3 предложения из спеки), далее требования.

- [ ]   3. Перенеси каталог изменения:
       `specs/<id>-<slug>/` → `specs/archive/<ГГГГ-ММ-ДД>-<id>-<slug>/`
       (в git-проекте — `git mv`, дата — день закрытия).

- [ ]   4. Проверь согласованность: суммарная спека `_system/` не содержит дублей
       R# в одном домене и «призраков» удалённых требований (ссылки в других
       доменах — поправь).

- [ ]   5. Финальный коммит. В команде — только **после мержа PR** (спека системы
       должна двигаться вперёд только реально влитой работой); в соло — сразу.

- [ ]   6. У изменения есть внешний ID задачи и к таск-трекеру есть MCP/API?
       Предложи пользователю перевести задачу: если в `rules.md` есть таблица
       переходов — по ней, иначе — предложи закрыть. Разрешение запроси
       инструментом вопроса с вариантами («Перевести в <статус>» / «Не трогать») —
       внешнее состояние меняем не самовольно.

- [ ]   7. Если в корне проекта есть `MINDMAP.md` и изменение было крупным
       (новый модуль, ≈10+ файлов) — предложи пользователю обновить карту
       (скилл `mindmap-sync` из набора `mindcode`; если его нет — просто
       упомяни, что карта устареет). Нет `MINDMAP.md` — шаг пропусти.

- [ ]   8. Отчитайся: куда влит домен, путь в архиве, коммит. Цикл изменения
       завершён — явно сообщи: «Цикл завершён. Следующее изменение — /spec-1-specify».

## Gotchas

- **Архив без вердикта** — «и так сойдёт» ломает главный контракт фреймворка:
  в `_system/` попадает только проверенная правда.
- **Дельта без домена** — поле «Домен» пустое: заполни с пользователем, не выдумывай
  молча (но предложи вариант).
- **Конфликт дельт** — два изменения меняли одно требование: вливай то, что
  реально в коде; второе потребует переработки — сообщи пользователю.
- **Архив в PR** — если команда вливает архив в тот же PR, что и код: дифф спеки
  системы шумит; выберите одну конвенцию и держитесь её.
- **Полуархив** — перенёс каталог, а дельты не влил (или наоборот): это не закрытие,
  откатывай и доделывай.
