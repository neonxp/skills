# Формат MINDMAP.md

`MINDMAP.md` — ментальная карта архитектуры проекта в обычном Markdown. Отображается
инструментом [markmap](https://markmap.js.org): заголовки и списки становятся ветвями дерева.
Рядом может лежать `MINDMAP.html` — автономный офлайн-просмотрщик, собранный из
`assets/template.html` скилла.

Это стайлгайд, а не строгая грамматика: markmap понимает обычный Markdown. Ограничения ниже —
для того, чтобы карта оставалась ментальной картой, а не превратилась в дамп.

Скелет карты с готовым frontmatter — `assets/mindmap-template.md`. Настройки (`title`,
`initialExpandLevel`, …) можно переопределять в frontmatter каждой карты — просмотрщик
применяет их поверх значений по умолчанию.

## Структура

Разделы `##` **фиксированы** — не переименовывайте и не добавляйте свои верхние разделы,
вся вариативность — на уровнях `###` и ниже (исключение — корневая карта монорепы,
см. [example-monorepo-root.md](example-monorepo-root.md)):

1. **Слои и домены** — из каких частей состоит система; здесь же модели данных с полями.
2. **Ключевые потоки** — как данные и события перемещаются и **преобразуются** между
   частями: что на входе, что меняется, где хранится, что на выходе (цепочки со стрелками `→`).
3. **Кросс-функциональное** — авторизация, конфигурация, наблюдаемость, тесты, релизы.
4. **Структура файлов** — последний раздел: файлы репозитория и назначение каждого
   (правила агрегации ниже).

- `#` — единственный корень: `ИмяПроекта — чем является система` (одно предложение).
- `###` — домен/слой/поток: `Backend (Go)`, `Оформление заказа`.
- `####` — модуль/подсистема: `ИмяМодуля — русское описание ответственности`.
- Списки `-` — перечисления внутри узла (шаги потоков, поля моделей, топики Kafka, файлы).

Глубина не ограничена жёстко: `#` → `##` → `###` — обязательный скелет, глубже — по мере
нужды. Просмотрщик сворачивает узлы ниже третьего уровня (initialExpandLevel в
`assets/template.html`), так что глубина не портит обозримость. Узел глубже третьего
уровня — только если несёт самостоятельную ответственность, а не деталь родителя.

## Модели данных (внутри «Слоёв и доменов»)

Модели — обязательная часть доменной ветки: сущности БД, ключевые DTO и контракты
(события Kafka, API-модели). Модель — потомок узла-владельца:

- `##### ИмяМодели (где живёт)` — например `Order (БД: таблица orders)`,
  `CreateOrderRequest (DTO API)`, `OrderCreated (событие Kafka)`.
- Каждое поле — отдельная строка строго в формате:

  `- <имя поля> (<тип: string/int/float/bool/timestamp/enum/…>) — <описание>`

  Пример: `- status (enum: new/done) — состояние заказа`.
- Служебные поля агрегируйте: `- created_at, updated_at (timestamp) — метки времени`.
- Вносите модели, существенные для понимания системы; в модели — ключевые по смыслу поля.

## Структура файлов (последний раздел)

- `###` — директория: `` ### `cmd/server/` ``; файлы — строки списка под ней.
- Каждый файл — одна строка с обязательным комментарием:
  `- `main.go` — точка входа: конфигурация и запуск сервера`.
- **Агрегация**: пачки однотипных файлов (>5) — одна строка на пачку:
  `- `web/icons/*.svg` (120 шт.) — иконки интерфейса`. Если пачек слишком много —
  агрегируйте до уровня директории: `- `src/components/` — 40 UI-компонентов`.
- Не включайте: `.git`, `node_modules`, `vendor`, артефакты сборки, lock-файлы,
  IDE-конфиги, кэши. Строка «просто файл» без описания недопустима.

Глубина не ограничена жёстко: `#` → `##` → `###` — обязательный скелет, глубже — по мере
нужды. Просмотрщик сворачивает узлы ниже третьего уровня (initialExpandLevel в
`assets/template.html`), так что глубина не портит обозримость. Узел глубже третьего
уровня — только если несёт самостоятельную ответственность, а не деталь родителя.

## Стиль узлов

- Формула узла: **идентификатор из кода — русское описание через тире**.
  Имена модулей, пакетов и технологий — как в коде (`internal/orders`, Kafka, PostgreSQL);
  описание — по-русски, одним смысловым блоком, без пунктуационного мусора.
- Описание отвечает на вопрос «за что это отвечает», а не «из каких файлов состоит».
- Потоки записываются цепочками: `Витрина → internal/api → internal/orders → Kafka → billing`.
- Заголовок — не абзац: длинные перечисления и цепочки длиннее ~3 звеньев оформляйте
  списком шагов под узлом (см. пару ❌/✅ ниже).
- Inline-разметка: `` `code` ``, **жирный**, [ссылки](https://example.com) — по необходимости.

## Хорошо и плохо: узлы

❌ `#### internal/orders/handler.go — обработчик HTTP` — файл, а не модуль.
✅ `#### internal/orders — жизненный цикл заказа, saga выплат`.

❌ `#### internal/api — API` — тафтология вместо ответственности.
✅ `#### internal/api — HTTP-роутинг, middleware, OpenAPI-спека`.

❌ `#### internal/utils — вспомогательные функции` — тривиальные хелперы без своей ответственности.
✅ нетривиальная shared-библиотека — полноценный узел: `#### internal/auth — JWT-мидлварь, роли, сессии`.

❌ `### PostgreSQL, Redis, Kafka` — технологии без ролей.
✅ отдельные узлы: `#### PostgreSQL — основное хранилище, миграции goose`, `#### Redis — кэш каталога, сессии`.

❌ `##### CreateUser — валидация и резерв склада` — функция не несёт ответственности
подсистемы.
✅ глубина — для подсистем, моделей данных и их групп; сценарии функций — в «Ключевых потоках».

❌ `#### Прочее` — узел-помойка.
✅ узла не существует: содержимое либо не заслуживает узла, либо это отдельный домен.

❌ «Заказ проходит через несколько сервисов и попадает в биллинг» — проза.
✅ `Витрина → internal/api → internal/orders → Kafka → internal/billing` — цепочка.

❌ `### Основной конвейер публикации` с цепочкой из 8 звеньев в заголовке — стена текста
на 6 строк, нечитаемо.
✅ цепочка короче ~3 звеньев — в заголовке; длиннее — списком шагов под узлом:
  - `Feed.Retrieve` (ticker) → `application.inChan`
  - дедуп: `db.Exists` / `db.Append` → fan-out
  - `Target.Send` → `BuildMessage` → `processHTML`
  - `bluemonday.Sanitize` → API мессенджера

## Объём

Объём подбирается по масштабу проекта; верхняя граница полосы — **потолок, а не цель**:
30 честных узлов лучше 80 раздутых.

| Масштаб | Узлов (семантика) | Детализация |
| --- | --- | --- |
| Мелкий: до ~2k строк, 1–3 модуля | 20–40 | поля — только у 1–2 центральных моделей |
| Средний: ~2–50k строк, 4–12 модулей | 40–120 | центральные сущности (2–5 моделей) с полями |
| Крупный: >50k строк, >12 модулей, монорепа | 100–150 | поля — только у 2–3 ключевых моделей, остальное — имена моделей; жёсткая агрегация |

- Семантическая часть — без ветки «Структура файлов»: она лимитируется только
  агрегацией и считается отдельно.
- Верхние уровни (до `###`) держат карту обозримой; глубина не лимитируется — глубокие
  узлы сворачиваются в просмотрщике.
- Счёт узлов — семантическая часть (до раздела «Структура файлов»):
  `awk '/^## Структура файлов/{exit} /^(#{1,6} | *- )/{n++} END{print n+0}' MINDMAP.md`
- Вся карта целиком: `grep -cE '^(#{1,6} |\s*- )' MINDMAP.md`
- Примеры в этом документе показывают формат, а не целевой объём для вашего проекта.
- Если узлов больше 150 — укрупняйте ветви (объединяйте родственные модули в один узел),
  а не удаляйте домены.

## Что НЕ включать

- Функции и классы — нигде. Отдельные файлы — только в разделе «Структура файлов»;
  в семантических разделах файлы не упоминаются — карта про ответственность, не про файлы.
- Тривиальные хелперы и мелкую обвязку. Но нетривиальные shared-библиотеки (auth-мидлварь,
  общий event-bus, graceful-shutdown) — полноценные узлы: у них есть своя ответственность.
- Сгенерированный код как отдельные узлы (`*_pb.go`, миграции автогенерации) — максимум
  пометка внутри узла-владельца.
- Историю изменений,TODO, инструкции по запуску — для этого есть README.

## Чего избегать

- Блоков кода (```) и таблиц — в дереве они выглядят тяжело и ломают компактность узлов.
- Формул и любого синтаксиса, требующего плагинов markmap (KaTeX, подсветка): собранный
  офлайн-HTML рендерит их без стилей.
- Пустых узлов-заглушек («Разное», «Прочее») — лучше удалить ветвь, чем раздувать её мусором.
