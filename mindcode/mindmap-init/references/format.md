# Формат MINDMAP.md

`MINDMAP.md` — ментальная карта архитектуры проекта в обычном Markdown. Отображается
инструментом [markmap](https://markmap.js.org): заголовки и списки становятся ветвями дерева.
Рядом может лежать `MINDMAP.html` — автономный офлайн-просмотрщик, собранный из
`assets/template.html` скилла.

Это стайлгайд, а не строгая грамматика: markmap понимает обычный Markdown. Ограничения ниже —
для того, чтобы карта оставалась ментальной картой, а не превратилась в дамп.

Скелет карты с готовым frontmatter — `assets/mindmap-template.md`. Настройки (`title`,
`initialExpandLevel`, …) можно переопределять в frontmatter каждой карты — просмотрщик
применяет их поверх значений по умолчанию.

## Структура

- `#` — единственный корень: `ИмяПроекта — чем является система` (одно предложение).
- `##` — крупные разделы. Типовая тройка (адаптируйте имена под проект):
  - **Слои и домены** — из каких частей состоит система.
  - **Ключевые потоки** — как данные и события перемещаются и **преобразуются** между
    частями: что на входе, что меняется, где хранится, что на выходе (цепочки со стрелками `→`).
  - **Кросс-функциональное** — авторизация, конфигурация, наблюдаемость, тесты, релизы.
- `###` — домен/слой/поток: `Backend (Go)`, `Оформление заказа`.
- `####` — модуль/подсистема: `ИмяМодуля — русское описание ответственности`.
- Данные включайте явно: сущности БД, ключевые DTO и контракты (события Kafka, API-модели)
  так же важны для понимания системы, как модули. Форма — узел `### Данные` внутри домена
  или список ключевых сущностей под модулем-владельцем.
- Списки `-` — перечисления внутри узла (топики Kafka, схемы БД, шаги потока).

Глубина не ограничена жёстко: `#` → `##` → `###` — обязательный скелет, глубже — по мере
нужды. Просмотрщик сворачивает узлы ниже третьего уровня (initialExpandLevel в
`assets/template.html`), так что глубина не портит обозримость. Узел глубже третьего
уровня — только если несёт самостоятельную ответственность, а не деталь родителя.

## Стиль узлов

- Формула узла: **идентификатор из кода — русское описание через тире**.
  Имена модулей, пакетов и технологий — как в коде (`internal/orders`, Kafka, PostgreSQL);
  описание — по-русски, одним смысловым блоком, без пунктуационного мусора.
- Описание отвечает на вопрос «за что это отвечает», а не «из каких файлов состоит».
- Потоки записываются цепочками: `Витрина → internal/api → internal/orders → Kafka → billing`.
- Inline-разметка: `` `code` ``, **жирный**, [ссылки](https://example.com) — по необходимости.

## Хорошо и плохо: узлы

❌ `#### internal/orders/handler.go — обработчик HTTP` — файл, а не модуль.
✅ `#### internal/orders — жизненный цикл заказа, saga выплат`.

❌ `#### internal/api — API` — тафтология вместо ответственности.
✅ `#### internal/api — HTTP-роутинг, middleware, OpenAPI-спека`.

❌ `#### internal/utils — вспомогательные функции` — тривиальные хелперы без своей ответственности.
✅ нетривиальная shared-библиотека — полноценный узел: `#### internal/auth — JWT-мидлварь, роли, сессии`.

❌ `### PostgreSQL, Redis, Kafka` — технологии без ролей.
✅ отдельные узлы: `#### PostgreSQL — основное хранилище, миграции goose`, `#### Redis — кэш каталога, сессии`.

❌ `##### CreateUser — валидация и резерв склада` — функция не несёт ответственности
подсистемы.
✅ глубина — для подсистем, моделей данных и их групп; сценарии функций — в «Ключевых потоках».

❌ `#### Прочее` — узел-помойка.
✅ узла не существует: содержимое либо не заслуживает узла, либо это отдельный домен.

❌ «Заказ проходит через несколько сервисов и попадает в биллинг» — проза.
✅ `Витрина → internal/api → internal/orders → Kafka → internal/billing` — цепочка.

## Объём

- Цель: **60–150 узлов** суммарно. Маленькому проекту достаточно 20–30. Верхние уровни
  (до `###`) держат карту обозримой; глубина не лимитируется — глубокие узлы сворачиваются
  в просмотрщике.
- Счёт узлов: `grep -cE '^(#{1,6} |\s*- )' MINDMAP.md`
- Если узлов больше 150 — укрупняйте ветви (объединяйте родственные модули в один узел),
  а не удаляйте домены.

## Что НЕ включать

- Отдельные файлы, функции, классы — карта близка к диаграмме модулей, не классов.
- Тривиальные хелперы и мелкую обвязку. Но нетривиальные shared-библиотеки (auth-мидлварь,
  общий event-bus, graceful-shutdown) — полноценные узлы: у них есть своя ответственность.
- Сгенерированный код как отдельные узлы (`*_pb.go`, миграции автогенерации) — максимум
  пометка внутри узла-владельца.
- Историю изменений,TODO, инструкции по запуску — для этого есть README.

## Чего избегать

- Блоков кода (```) и таблиц — в дереве они выглядят тяжело и ломают компактность узлов.
- Формул и любого синтаксиса, требующего плагинов markmap (KaTeX, подсветка): собранный
  офлайн-HTML рендерит их без стилей.
- Пустых узлов-заглушек («Разное», «Прочее») — лучше удалить ветвь, чем раздувать её мусором.
